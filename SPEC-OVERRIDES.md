# SPEC overrides

`SPEC.md` is frozen. Decisions that supersede it are appended here, dated and numbered, newest last. Each entry quotes the SPEC line it overrides, states the new rule and the reason. Earlier implementation adjustments (ADJ-01..ADJ-30) live in `docs/00-overview.md`; this file records owner decisions that change the specification itself.

## 1. Language zones (2026-11-10, P9)
- **Overrides** SPEC.md §0: `REPO_LANGUAGE: Vietnamese              # prose of agents, skills, rules, docs, templates, journal. Change to "English" to switch.`
- **New rule — three language zones, by reader:**
  1. *Zone 1, AI-facing, English:* every `agents/*.md` body, `skills/*/SKILL.md` and `references/*`, `handbook/*.md`, `workflows/**`, `templates/project/claude/rules/*`, `templates/project/CLAUDE.md.tmpl`, the repo's own `CLAUDE.md`, `README.md`, `docs/**` (except the historical records `docs/requirements/**` and `docs/acceptance/**`), `evals/**`, script `--help` text, comments and messages.
  2. *Zone 2, owner-facing, Vietnamese:* exactly one file, `GUIDE-VI.md` (name kept in `scripts/vi-guide.conf`). It is the owner's control panel; its section 9 is the log of owner decisions and requests that every session reads. No other Vietnamese prose in the repo, except the allowlist enforced by `scripts/check-lang.py` (`scripts/vi-strings.json`, `templates/artifacts/vi/**`, historical records, CHANGELOG entries up to 0.3.0, and the first line of `README.md` pointing to the guide).
  3. *Zone 3, artifacts produced inside a project:* prose language chosen by the new slot `output_language` in `.team/config.json` (enum `vi` | `en`, default `vi`). Templates come from `templates/artifacts/vi/` (Vietnamese headings/hints) or `templates/artifacts/` (English).
- **Anchors** (machine-read strings listed in `scripts/anchors.txt`: `Approved-by:`, `## Sources`, `## Definition of Done`, `## Assumptions decided by the team`, verdict and status keywords, `STD-*` codes, IDs, branch and commit patterns, intake fields, PR-body headings, JSON keys, file names) never change language in any zone; `scripts/check-lang.py` fails on any translated form.
- **Reason:** Claude reads AI-facing text on every call; Vietnamese with diacritics costs far more tokens than English for the same content (`docs/research/language-switch.md` measures it) and English is the language the reference kits and Claude Code docs use. The owner keeps reading and writing Vietnamese where it matters to him: the control file and the artifacts of his projects.

## 2. Model routing by the shape of the work (2026-11-11)
- **Overrides** SPEC.md §3: `Model routing: strongest model where a mistake is most expensive. haiku for triage/mechanical; sonnet for orchestration, dev, writer, maintainer, devops; opus for analyst, researcher, architect, designer, reviewer, qa, coach.` and the model column of the §3 role table.
- **New rule:** fable for the roles that coordinate many tasks (team-leader, tech-lead); opus for a role that carries out one concrete job alone and whose mistakes are expensive (dev, maintainer, devops, architect, designer, reviewer, qa); sonnet for reading, analysis and documentation (analyst, researcher, coach, writer); haiku for classification and mechanical work. ADJ-10 still applies (designer runs sonnet for size S/M). Never switch model mid-session.
- **Where it lives:** the `model` frontmatter of `agents/*.md` (the value Claude Code applies), the sample `models` in `templates/project/team/config.json`, `docs/02-team.md`, the `make-agent` skill and its agent template.
- **Reason:** the leads hold the whole feature in view and route many tasks, so they get the model best at long multi-task coordination; one-job roles that write code or change the system get opus; analysis and writing are cheap to redo and run on sonnet.

## 3. CLAUDE.md describes the project, and the team keeps it true (2026-11-11)
- **Overrides** SPEC.md §10: `<project>/CLAUDE.md (block between <!-- team:start --> and <!-- team:end -->, ≤ 25 lines, inserted, never overwriting)` and the §12 appendix note `CLAUDE.md ≤ ~60 lines`.
- **New rule:** the project's CLAUDE.md has two team-kept blocks. The project block (`<!-- project:start -->…<!-- project:end -->`, ≤ 150 lines, above the team block) states what the system is, its commands (copied from `cmd.*`), layout, domain terms, conventions and gotchas. The team block (≤ 25 lines) stays as before. The whole file stays ≤ 200 lines. `/team:onboard` writes the project block from the takeover reports; an old CLAUDE.md is adopted into it and the ai-readiness keep / cut / rewrite is applied, with one reason row per cut or corrected line in `onboarding.md`. `/team:asbuilt` (writer) updates it after every feature; `/team:retro` (coach) reports drift under `## CLAUDE.md`. Text outside both blocks is the human's and is never edited. `scripts/check-claude-md.py` is the machine check.
- **Where it lives:** `skills/onboard`, `skills/asbuilt`, `skills/retro`, `skills/takeover`, `agents/writer.md`, `hooks/role-policy.json` (writer may write `CLAUDE.md`), `templates/artifacts/claude-md.md` (+ `vi/`), `templates/project/CLAUDE.md.tmpl`, `templates/artifacts/{asbuilt,retro}.md`.
- **Reason:** the owner found that a CLAUDE.md holding only the team block never described the project and never changed after onboard. Every agent in every session reads CLAUDE.md first, so the project facts belong there and must follow the code; 60 lines cannot hold the commands, layout and traps of a real system, and Claude Code's guidance is to stay under about 200 lines.

## 4. Run independent work at the same time (2026-11-12)
- **Overrides** SPEC.md §8 `.team/config.json` defaults: `limits{max_rework:3, max_attempts:3, max_questions_round:2, max_parallel_dev:2, …}`.
- **New rule:** whenever several calls do not need each other's results, they go out in ONE message so they run at the same time. Build dispatches in rounds: each round carries every dev for a ready task that shares no file with a task in flight, every rework and every review that can start, up to the dev and reviewer headcount; it never waits for a whole wave to be ticked. Independent Explore questions go out together. A request with several independent items becomes one intake per item and runs as one wave. The config template ships `max_parallel_dev: 4` and `headcount` reviewer 4, architect 1, every other role 2. Merges stay serial, two tasks sharing a file never run together, and the stages of one feature stay in order.
- **Where it lives:** `skills/build`, `agents/tech-lead.md`, `agents/team-leader.md`, `skills/intake`, the Explore steps of `skills/{analyze,design,architect,takeover}` and `agents/{analyst,architect,designer}.md`, `handbook/tool-map.md`, `templates/project/team/config.json`, `docs/01-process.md`.
- **Reason:** the owner asked that a request run on many agents at once instead of wasting time. In the first real project 496 of 522 dispatch messages carried a single Agent call, and the 2-dev cap held back plans whose levels were 5–7 tasks wide. Running agents together costs about the same tokens for the same work, but spends them in a shorter time.

## 5. Hooks remind, they do not block (2026-11-13)
- **Overrides** SPEC.md principle P3 ("anything that must not go wrong is blocked by a hook, a permission or a script") for the kit's own hooks, and the "Blocks (exit 2)" behavior of `protect.sh`, `check-git.sh`, `role-policy.sh`, `stop-check.sh`.
- **New rule:** `.team/config.json` key `enforcement`: `"warn"` (default; a missing key means warn) or `"block"`. In warn mode every check still runs and its message reaches Claude (`RULE (reminder, not enforced) …` in additionalContext, or a systemMessage at Stop), but the tool runs and the agent may stop; stop-check skips the lint/test pass. In block mode the hooks exit 2 as before. Skills, agents, the handbook and STD codes are the rules the team follows; a reminder is a rule to keep or to justify in the report. Gates (`team.py`) and Claude Code permissions are unchanged.
- **Where it lives:** `scripts/lib.sh` (`enforcement`, `remind`, `block`), `scripts/teamlib.py` (`enforcement`, `main`), `scripts/stop-check.sh`, `templates/project/team/config.json`, `templates/schemas/config.schema.json`, `docs/06-install.md`, `docs/guides/incidents.md`, `GUIDE-VI.md`.
- **Reason:** the owner asked that hooks block nothing: skills and rules are working rules, and this much blocking leaves nobody able to work (GUIDE-VI.md section 9, 2026-11-13). In the first real project the main session was stopped on read-only commands at least 30 times and could not run the smoke tests the owner asked for.

## 6. Tasks are vertical slices, and agents read lean (2026-11-13)
- **Overrides** SPEC.md §4: `Tasks are 2–5 minutes with concrete file paths.`
- **New rule:** a task is one vertical slice: one behavior with its tests, at most 5 files, about 15–30 minutes of work, still with concrete file paths and a test file. Artifacts stay small because every agent re-sends what it reads on every turn: spec.md S 60 / M 150 / L 250 lines, design.md M 300 / L 500 lines, plan.md 150 lines, at most 4 lines per task; `tasks.md` holds no progress log. Agents read by section, never a large file whole, and never re-read a file already in context.
- **Where it lives:** `skills/handbook`, `skills/plan`, `skills/design`, `skills/analyze`, `skills/build` (+ `references/handoffs.md`), `agents/{dev,reviewer,tech-lead}.md`, `templates/artifacts/tasks.md` (+ `vi/`), `docs/01-process.md`.
- **Reason:** the owner saw agents reading for most of their run and acting little. In the first real project on kit 0.6.x, cache reads were 85–93% of all tokens; a dev needed 61 turns per 2–5 minute task (24 before its first code edit), and every task paid a dev start-up, a review and a merge, so the overhead outweighed the work.

## 7. Session lanes: several sessions on one project (2026-11-14)
- **Overrides** SPEC.md §8: `Gitignored runtime files: \`.team/current.json\` {feature, stage, agent, started_at}, …` and every SPEC step that writes `current.json` at the start of a stage; the build's single `.team/active-build` was already per feature (ADJ-31).
- **New rule:** a project can run several Claude sessions at once, each in its own lane. The position of a session lives in `.team/session/<session_id>.json` and is written by `team.py claim <ID> --stage <stage> --agent <role>`; `.team/current.json` is retired. Different items run in parallel without a question; the same item held by another live session is a question for the human (leave it / take it over / do something else); the same file goes one session at a time (a task whose files another session holds waits for a later round), different files run in parallel. IDs come from `team.py new-id` (atomic). The main tree's branch never changes: feature branches are merged and tested in their own worktree. A lane ends with its Claude process; SessionEnd releases it. Rules: `handbook/sessions.md`.
- **Where it lives:** `scripts/team.py` (claim, release, sessions, new-id, busy; `Session` column; wave), `scripts/lib.sh`, `scripts/teamlib.py`, `scripts/session-start.sh`, `scripts/protect.sh`, `scripts/handoff.sh`, `hooks/role-policy.json`, `handbook/sessions.md`, every stage skill and role agent (the claim step), `skills/{intake,build,verify,pr,status}`, `skills/run/references/parallel-wave.md`, `workflows/quick.md`, `agents/{team-leader,tech-lead,qa}.md`, `templates/project/team/config.json`, `templates/schemas/config.schema.json`, `scripts/tests/test_sessions.sh`, `docs/01-process.md`.
- **Reason:** the owner runs 2–3 sessions on one project and kept hitting conflicts on the same file (GUIDE-VI.md section 9, 2026-11-14). In `erp_ai` three sessions (2d940539 building FEAT-007, 6c38287b finishing FEAT-004/005/006, d6349641 editing code directly) shared one repo: all of them wrote the one `.team/current.json`, and one session refused to write it "to not step on the other"; one session switched the main tree to `team/FEAT-003` while the others worked there; uncommitted code of one session was found by another, which could not tell whose it was; the same request sent to two sessions became both CHG-001 and a direct implementation; a `bench migrate` run from another branch dropped a DocType from the shared site and turned the other session's suite red.

## 8. Few, larger tasks; review by risk (2026-11-15)
- **Overrides** SPEC.md §5 build loop: `reviewer (fresh context): tier 1 matches spec → tier 2 quality; findings carry STD codes` … `tech-lead ticks the task, writes review-NN.md, merges into team/<ID>, runs cmd.test` (a separate review before every task's merge), and entry 6 of this file: `a task is one vertical slice: one behavior with its tests, at most 5 files, about 15–30 minutes of work`.
- **New rule:** a task delivers 1–4 criteria end to end, roughly 100–400 changed lines with their tests, at most 6 files; size M has at most 6 tasks, size L at most 12, and a bigger plan is a sign of several features. Small pieces fold into the task they serve. A task marked `[risk]` (authorization or secrets, migration or schema, money or data deletion, a contract used outside the feature, shared state) is reviewed before its merge as before. Every other task is merged once the tech-lead has checked its red-then-green evidence and `cmd.test` is green, and the merged tasks are reviewed together in one checkpoint call (every 3 merged tasks and at the end); the build is not done while a merged commit is unreviewed. A finding is `major` only for a missed criterion or wrong behavior, a test that cannot fail or a skip, a security or data-loss risk, a broken contract, an edit outside the touchpoints, or an edge the criteria or design name with no test; everything else is minor and never blocks. A fix that changes only tests is merged on its red-then-green evidence; a production fix gets a scoped re-review. The tech-lead decides design points that change no criterion, outside contract, schema, ADR or outside file; the rest goes to the designer in one call per build stop and is answered in `design.md`; the architect reviews a design once.
- **Where it lives:** `skills/plan`, `skills/build` (+ `references/handoffs.md`), `skills/design`, `skills/architect`, `agents/{tech-lead,reviewer,dev}.md`, `handbook/STD.md` (Finding format; `STD-short.md` regenerated), `templates/artifacts/{tasks,review}.md` (+ `vi/`), `docs/01-process.md`, `scripts/vi-strings.json`.
- **Reason:** the owner saw tasks split too small, each running the whole chain, mostly review, for little output (GUIDE-VI.md section 9, 2026-11-15). In `erp_ai` on kit 0.6.4 (2026-11-14/15, 855 subagent runs) the median code commit changed 5 production lines and FEAT-007 was planned as 180 tasks; there were 333 dev and 301 reviewer calls, and the first dev pass, the part that writes the code, was only about a quarter of the subagent cost: tech-lead orchestration took about 29%, review 15%, rework 7%, designer and architect rulings 15%.

## 9. Tests once per round, not after every merge (2026-11-15)
- **Overrides** SPEC.md §5 build loop: `tech-lead ticks the task, writes review-NN.md, merges into team/<ID>, runs cmd.test` (a full suite after every task merge), as carried by entry 8.
- **New rule:** after each merge the tech-lead runs only the merged task's `test:` files with `cmd.test_one`; the full `cmd.test` runs once per round, after the round's last merge, and a green run ticks every task merged in the round. A red run is traced to the merge that turned the test red (that test file at each merge of the round, oldest first); that task stays unticked and one dev fixes it on `team/<ID>-fix-K`, merged first in the next round. Nobody calls a dev only to rerun tests for evidence; a dev runs each test in one foreground call and reruns only after a change.
- **Where it lives:** `skills/build` (+ `references/handoffs.md` § Tests in the loop), `agents/{tech-lead,dev}.md`, `docs/01-process.md`, `docs/04-profile.md`, `templates/schemas/profile.schema.json`.
- **Reason:** the owner saw review and test runs take most of the time and tokens (GUIDE-VI.md section 9, 2026-11-15). In `erp_ai` (kit 0.6.2–0.6.4) a module test took about 11 s on a free site, but devs spent 70–90% of their time running or waiting for tests: every run holds the one shared site, and 112 full suites of 3–20 minutes (about 15 hours) ran, about one per merge. One full run per round covers all of its merges and keeps the end-of-build `cmd.test` as the evidence the DoD needs.

## 10. Product before paperwork: try it, read back, lean docs and tests (2026-11-16)
- **Overrides** SPEC.md §4 stage 7 acceptance (qa runs every criterion on the commit; the product meets a real instance only at release, staging UAT) and §5 artifacts (`diff.patch` for the writer, a report file per dev call, review/ruling files per call), and the line caps of entry 6.
- **New rule:** before `accepted`, qa runs the commit on a live instance with the feature switched on, walks the main flow where the requester works (a browser flow through any browser MCP), and writes ≤ 3 steps the human can follow; green tests with a broken walk-through is `rework`. The analyst writes a ≤ 5-line read-back the team-leader shows the human in every mode; every criterion quotes what it serves; caps S 5 / M 12 / L 24 criteria; extra ideas are Team additions, not built unless picked; what was asked for is switched on. A feature folder holds only the stage artifacts (intake, questions, spec, research, arch-impact, design, plan, tasks, review-NN, acceptance, asbuilt, pr-body, source-*), each under a KB budget (`limits.doc_kb`), checked by `team.py docs` and by the write hook (reminder by default); the diff is read from git; rulings and reports live in return messages, commit bodies and in-place edits; docs are committed once per stage; journals are appended. Tests cover what the criteria and design name (STD-TEST-8, STD-TEST-9); ADR constraints are checked in review. Intake sizes the change, not its importance.
- **Where it lives:** `scripts/team.py` (`docs`, status line), `scripts/protect.sh`, `scripts/tests/test_hooks.sh`, `templates/project/team/config.json` + `templates/schemas/config.schema.json` (`limits.doc_kb`, `limits.max_criteria`), `skills/{analyze,verify,build,design,plan,asbuilt,architect,intake,handbook,run,using-team,pr}`, `skills/asbuilt/references/writing-rules.md`, `skills/architect/references/decision-test.md`, `skills/build/references/handoffs.md`, `agents/{team-leader,analyst,qa,tech-lead,dev,writer}.md`, `handbook/STD.md` (STD-TEST-8, STD-TEST-9, checklist item 3), `handbook/tool-map.md`, `templates/artifacts/{spec,acceptance}.md` (+ `vi/`), `templates/project/claude/rules/tool-map.md.tmpl`, `scripts/allowed-tools.txt`, `scripts/vi-strings.json`.
- **Reason:** the owner saw the process outweigh the product and miss what he wanted (GUIDE-VI.md section 9, 2026-11-16). In `erp_ai` over 5 days (about $2,600 API-equivalent, 1,522 subagent runs): docs/team reached 18.3 MB against 0.54 MB of production code and 2.4 MB of tests; 64% of feature-doc lines were `diff.patch` copies of git; FEAT-007 alone had 204 files (39 design addendum/fix files, 19 journal parts, 11 audits); 279 commits touched only process docs. Every item was sized L and one-sentence requests became 12–64 criteria with 8–45 team assumptions nobody read back. Each feature was `accepted` on its branch, yet the owner found every failure on his site himself (the bot could not create a user, the indicator never stopped, auto-assign never ran), and qa had no browser tool, so every UI check ended `NOT VERIFIABLE`.

## 11. One checkpoint per round: test and review together (2026-11-16)
- **Overrides** SPEC.md §5 build loop (`reviewer (fresh context) …` / `tech-lead ticks the task, writes review-NN.md, merges into team/<ID>, runs cmd.test`, a review and a test per task) and the parts of entries 8 and 9 of this file that still ran per task: a `[risk]` task reviewed before its merge, and the merged task's `test:` files run after each merge.
- **New rule:** the dev's own red-then-green run is the only test per task. After a round, the tech-lead merges every finished task and fix, `[risk]` included, one after another with no test in between, then runs the full `cmd.test` once (red → the merge that broke it is traced, as in entry 9). Then ONE reviewer call covers everything merged since the last review, `[risk]` tasks included, sent in the next dispatch round beside the devs; it is due when 3 merged tasks are unreviewed, a merged `[risk]` task is unreviewed, or nothing is left. A `[risk]` task is ticked only when that review leaves no blocker/major on it, so the tasks that depend on it wait for it. One dev fixes a review's findings on one fix branch; the next checkpoint marks them `ADDRESSED`/`NOT ADDRESSED`, with no separate re-review call. The build is done when every task is ticked, no blocker/major is open, and no production code was merged after the last review. Trade-off the owner accepted: a `[risk]` task's code, a migration included, runs on the team's test site before it is reviewed; it still cannot reach the base branch unreviewed.
- **Where it lives:** `skills/build` (+ `references/handoffs.md`), `agents/{tech-lead,reviewer,dev}.md`, `skills/plan`, `templates/artifacts/{tasks,review}.md` (+ `vi/`), `docs/01-process.md`, `scripts/vi-strings.json`.
- **Reason:** the owner asked why test and review must follow each dev at once when they can be done together (GUIDE-VI.md section 9, 2026-11-16). Dispatch rounds are synchronous, so every per-task test or review is time in which no agent works; on kit 0.6.4 the tech-lead of `erp_ai` ran tests 290 times in two days (about 4.2 hours), and 301 reviewer calls covered about 250 tasks.

## 12. Results first: fewer steps before code, no retest of an unchanged commit, progress the lead can see (2026-11-16)
- **Overrides** SPEC.md §4 sizes: `M (one module; data or API change; 1–5 person-days) → intake → analyze → [research if technical questions] → design → plan → build → verify → release`, and the acceptance and PR steps that rerun `cmd.test` on the commit the build already tested.
- **New rule:** a size-M new-feature goes from the spec straight to the plan; `plan.md` carries a `## Design` section of at most 40 lines (contracts and schema changes with exact names, touchpoints, the test per criterion). A separate design stage stays for size L and for the data-migration, integration and refactor playbooks. One research call per feature answers every open question at once; a later question is decided and recorded, or asked of the human. A green `cmd.test` stays valid for its commit: the build writes `tested: <sha> <summary>` in the journal, and verify and pr paste that line instead of running the suite again on the same commit (a rebase makes a new commit and reruns it). After every stage the team-leader tells the human, in at most 3 lines in `output_language`, what works now, what is left and what is needed from them. `team.py status` shows accepted work whose code is already in the main tree's branch as `DELIVERED`, with nothing left for the team, and `--brief` folds those items into one line.
- **Where it lives:** `scripts/team.py` (`delivered_in`, `next_cmd`, `--brief`), `scripts/tests/test_team_status.sh`, `scripts/anchors.txt`, `skills/{plan,design,research,verify,pr,run,status,build,analyze,asbuilt}`, `skills/build/references/handoffs.md`, `agents/{team-leader,qa,writer,tech-lead}.md`, `templates/artifacts/plan.md` (+ `vi/`), `workflows/new-feature.md`, `docs/01-process.md`.
- **Reason:** the owner wants results and to see the project move, not the team researching, reviewing and retesting for ever (GUIDE-VI.md section 9, 2026-11-16). In `erp_ai`, 184 of 1,535 agent calls came before any code (about 20% of the cost); FEAT-007 made 23 calls before its first dev (designer 10, researcher 6, architect 5); and 9 accepted items already merged into `develop` still read as pending pr and release work in the status table, the only view the owner got.
